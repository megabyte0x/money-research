# Timeline editing and IDs

The three source timelines remain the editorial text. `public/content/timeline-event-ids.json` is metadata: every source table row has one durable ID, separate from its date, label and row position. A text or date correction changes that row's `key`, **not** its `id`. A new row gets the next unused ID for its volume (for example, after the existing `evt-gold-0090`, use `evt-gold-0091`); never renumber older IDs after inserting or removing a row. Retire an ID when an event is withdrawn rather than reusing it for a different event.

`src/timeline-references.js` maps reviewed IDs to article sections. Add a mapping only after checking the destination discusses the specific event; otherwise the UI links to its source timeline. `src/timeline.js` pairs the small set of cross-volume duplicates that an editor has confirmed represent the same event. Do not merge on matching words or date alone. Split a bundled source row before pairing if only one of its events is shared. Price values can change in `observations.json` without changing event IDs or their reviewed links.

Run `npm run build` and `node --test --test-isolation=none tests/*.test.mjs` after editing. The build fails for unregistered, duplicate or stale source-event keys; tests validate registry coverage and section existence. These mechanical checks do **not** establish historical accuracy or editorial relevance for unmapped rows. The F06/D07 release gate still requires human review of the remaining events and composite claims.

If only an approximate period is supported, state it in the display date rather than inventing a day. For example, “Late 2008” sorts after mid-September but before November; that sort position is editorial approximation, not a precise event date.

`eventDateRange` in `src/timeline.js` now exposes a start, end, precision and approximation flag from each display date. The signed historical-year convention has **no year zero**: 1 BCE is `-1` and 1 CE is `+1`. A century or stated span supplies sortable bounds, not a claimed day of occurrence. For example, “c. 6th c. BCE” has bounds 600–501 BCE, while “c. 4600–4300 BCE” retains the whole approximate span. A halving occurs at its protocol block height; a displayed “~Apr 2028” is a forecast month and must remain visibly qualified. The current reader orders events by the first stated bound and still shows the original display date.

`workstreams/05/coverage.json` enumerates every current row with its ID, date bounds, proposed destination and review status. Its syntax-based composite flag is a triage cue, not an editorial finding. An existing link remains marked for recheck after chapter edits until its body and cited historical assertion are reviewed; an unlinked source-timeline row is explicitly an **unreviewed fallback**, not a completed relevance decision. Do not promote either state to a release claim.
